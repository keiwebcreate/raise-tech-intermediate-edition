## 1. 運用の考え方

| 考え方 | 内容 |

| 規模 | 課題のアプリ。同時に使う人は10人ほど（N-11）。いつも動かしておくのではなく、**使うときだけ作って動かす**（4章） |

## 2. 監視

### 2.1 何を見るか

障害に気づくための「大事な数か所」だけを見張り、メールで知らせる（ユーザーの決定、2026-11-21）。数を増やしすぎると、知らせが多くなって見なくなるため。

| # | 見るもの | どこで | 知らせる条件（目安） | 分かること |
|---|---|---|---|---|
| A1 | ALB が返した 5xx（500 番台のエラー） | CloudWatch（ALB の `HTTPCode_Target_5XX_Count`・`HTTPCode_ELB_5XX_Count`） | 5分間に 5 回以上 | アプリが落ちている・エラーを返し続けている |
| A2 | EC2 が生きているか | CloudWatch（ALB のターゲットの `UnHealthyHostCount`。EC2 の `StatusCheckFailed`） | 1 以上が 5分続く | Spring Boot か Nginx が止まった・EC2 そのものの故障 |
| A3 | アプリの ERROR のログ | CloudWatch Logs のメトリクスフィルター（`log.level` が `ERROR` の行を数える） | 5分間に 1 回以上 | 想定していない失敗（500）が起きた。中身はログで見る（logging.md 7.2） |
| A4 | RDS の空き容量 | CloudWatch（RDS の `FreeStorageSpace`） | 残り 2GB 未満 | DB がいっぱいになりそう |
| A5 | 費用 | AWS Budgets | 決めた金額の 80%・100% | 片付け忘れ・思わぬ費用（4章） |

- 知らせは **SNS（メールで知らせる仕組み）** の1つのトピックにまとめ、自分のメールアドレスに送る。メールアドレスは Terraform の変数で渡し、Git には書かない
- 知らせの条件の数字は目安。【デプロイで確かめる】ふつうに使っているときに知らせが来ないこと、わざと止めたときに来ることを確かめて直す

### 2.2 ふだん見るもの（知らせはしない）

| 見るもの | どこで | 使い方 |
|---|---|---|
| アクセスログ（API ごとの回数・時間・番号） | CloudWatch Logs Insights | 遅い API・4xx が多い API を探す（logging.md 7.2） |
| EC2 の CPU・RDS の CPU と接続数 | CloudWatch のメトリクス | 重くなったときの原因を探す |
| WARN のログ（ログインの失敗・盗まれた疑いのトークンなど） | CloudWatch Logs Insights | 使うたびに1回、増えていないかを見る |

### 2.3 ヘルスチェック

- ALB は、決まった住所を定期的に開いて、EC2 が生きているかを確かめる（ヘルスチェック）。今のアプリには、ログインなしで 200 を返す API がない
- 【デプロイで決める】Spring Boot Actuator の `/actuator/health`（DB につながるかも見る）を入れ、Nginx の中からだけ開けるようにする案。外に出すときは、中身（DB の名前など）を出さない設定にする

## 3. ログ

- 決まりは [logging.md](logging.md)。1行ずつ JSON（ECS）で標準出力に出す
- 【デプロイで確かめる】EC2 の CloudWatch エージェント（ログを送る道具）で、systemd が受け取った Spring Boot の出力を CloudWatch Logs のロググループ（例：`/raisetechtimeline/app`）へ送る。Nginx のエラーログも別のロググループへ送る
- 保存は **14日**（infrastructure.md）。それより古いものは自動で消える
- ログを探すときは、画面のエラーに出た `X-Request-Id`（リクエストの ID）か、日時と `userId` で絞る

## 4. 費用の管理と片付け（N-44）

### 4.1 決まり

- **使わないときは `terraform destroy` で全部片付ける**（ユーザーの決定、2026-11-21。トレロ風アプリと同じ）。ALB は止められず、置いているだけで費用がかかる。RDS は止めても7日たつと自動で動き出すため
- 使うときは `terraform apply` で作り直し、アプリを置き直す（7章）
- AWS Budgets で月の上限を決め、80%・100% でメールを受け取る（A5）

### 4.2 片付けるとき

1. 残したいデータがあるか決める
   - 残す：RDS のスナップショット（DB の写し）を手で取ってから片付ける。次に作るとき、そのスナップショットから RDS を作る【デプロイで決める：Terraform での書き方】
   - 残さない：そのまま片付ける（確認用のデータだけなら、こちらでよい）
2. S3 のバケットは、中にファイルがあると消せない。画像・動画も消してよいか確かめてから空にする
3. `terraform plan -destroy` で消えるものの一覧を見てから、`terraform destroy`
4. AWS のコンソールで、シドニーと CloudFront（全体）に残っているものがないかを見る。CloudWatch Logs のロググループと Parameter Store の値も、Terraform で作っていなければ残るので確かめる

### 4.3 費用がかかるもの（目安）

ALB・EC2・RDS・CloudWatch（ログの量・アラームの数）・S3（保存の量）・通信の量。【デプロイで確かめる】AWS の料金表と、Budgets・Cost Explorer の実際の金額で確かめて、ここに書く。NAT ゲートウェイ（高い）は使わない構成にしている（infrastructure.md）。

## 5. バックアップと戻し方（N-41）

| もの | バックアップ | 戻し方 |
|---|---|---|
| DB（RDS） | **自動バックアップ 7日分**（N-41）。毎日1回の写しと、それ以降の変更の記録で、7日以内の好きな時刻に戻せる（ポイントインタイムリカバリ） | 戻したい時刻を指定して、**新しい RDS を作る**（今の RDS は上書きされない）。アプリの接続先を新しい RDS に変えて、Spring Boot を起動し直す。【デプロイで確かめる】一度、実際に戻してみる |
| 画像・動画（S3） | バックアップはしない（課題の規模のため）。消した投稿の画像は戻らない | — |
| アプリ（jar・画面のファイル） | GitHub の main と、EC2 の1つ前の版（7章） | 1つ前の版に戻す（7.2） |
| 設定・秘密の値 | Terraform のファイル（Git）と Parameter Store | Terraform で作り直す。秘密の値は自分で入れ直す |

- 自動バックアップは RDS を消すと一緒に消える。片付ける前に残したいときは、手でスナップショットを取る（4.2）

## 6. 定期の作業

| いつ | 作業 | 誰が |
|---|---|---|
| 毎日 4:00（UTC） | 期限切れのリフレッシュトークンを DB から消す（`RefreshTokenCleanupJob`） | アプリが自動で |
| 1時間ごと | ログインの失敗の記録（メモリ）の古いものを消す（`LoginRateLimiter`） | アプリが自動で |
| 毎日 | S3 の `tmp/`（選んだが投稿していない画像・動画）のうち、1日たったものを消す（ライフサイクルの設定） | S3 が自動で |
| 毎日 | RDS の自動バックアップ | RDS が自動で |
| 使うたび | 知らせのメール・WARN のログ・費用を見る（2.2・A5） | 自分 |
| 月1回（動かしている間） | EC2 の OS（Amazon Linux 2023）の更新（`dnf upgrade`）。Java・Nginx も含む | 自分 |
| 片付けたとき | コンソールで残っているものがないか見る（4.2） | 自分 |

- 定期の片付けが動いたかは、INFO のログ「期限切れのリフレッシュトークンを N 件消しました」で分かる（logging.md 5章）

## 7. デプロイと戻し方

【デプロイで決める】詳しい手順は、AWS の講義・デプロイのイシューで決める（infrastructure.md 7章）。ここには運用の決まりだけを書く。

### 7.1 デプロイ

- main にマージした版だけを置く。置く前に、手元で `.\gradlew.bat check` と画面のチェックを通す（CI はまだない）
- 置くときは、**1つ前の jar と画面のファイルを残しておく**（すぐ戻せるように）
- DB の変更（Flyway の新しい SQL）があるときは、置く前に RDS のスナップショットを取る。Flyway は Spring Boot の起動のときに自動で流れ、戻す仕組みはないため
- 置いたあと：ログイン・投稿・画像の表示を確かめ、ERROR のログが出ていないかを見る

### 7.2 戻し方

| 戻す理由 | やること |
|---|---|
| アプリの不具合（DB の変更なし） | 残しておいた1つ前の jar・画面のファイルに戻し、Spring Boot を起動し直す |
| DB の変更を含む | 1つ前の jar では新しいテーブルの形と合わないことがある。置く前に取ったスナップショットから戻す（5章）か、直した版を新しく出す |

## 8. 秘密の値の入れ替え

秘密の値は Parameter Store（`SecureString`）に置き、Spring Boot は起動のときに読む（infrastructure.md 4章）。入れ替えたら Spring Boot を起動し直す。

| 秘密の値 | 入れ替えるとき | 入れ替えると起きること |
|---|---|---|
| JWT の鍵（`SNS_JWT_SECRET`） | 漏れた疑いがあるとき | 今のアクセストークン（15分）がすべて使えなくなる。ただしリフレッシュトークンは JWT ではないので、画面は自動でログインを延ばし、利用者はふつう気づかない（authentication.md 7.3） |
| すべての人を強制的にログアウトさせたい | 盗まれた疑いが広いとき | JWT の鍵の入れ替えに加えて、DB の `refresh_tokens` を取り消す（全員がもう一度ログイン） |
| DB のパスワード（`SNS_DB_PASSWORD`） | 漏れた疑いがあるとき・定期に変えたいとき | RDS のパスワードを変え、同じ値を Parameter Store に入れてから Spring Boot を起動し直す（その間は使えない） |
| AWS の鍵 | — | 使わない。EC2 はロール（IAM）で S3・Parameter Store を使う |

- 入れ替えの作業そのものも、コマンドの引数や画面のスクリーンショットに値を出さない

## 9. この文書で新しく決めたこと（確認をお願いします）

- 知らせる条件の数字（5分に 5 回の 5xx・ERROR は 1 回で知らせる・RDS の残り 2GB など）は目安。デプロイのときに直す
- 知らせは SNS の1つのトピックにまとめ、自分のメールにだけ送る
- ヘルスチェックは Spring Boot Actuator の `/actuator/health` を入れる案（デプロイのときに決める）
- S3 の画像・動画はバックアップしない
- DB の変更を含むデプロイの前に、RDS のスナップショットを取る
- 動かしている間は、月1回 OS を更新する
