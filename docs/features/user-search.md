# 機能定義書：ユーザー検索（フォローする人の探し方）

| 項目 | 内容 |
|---|---|
| 対象の機能 | US-01・US-02（[機能一覧](../features.md) 1.8） |
| 版 | 0.4（2026-11-21） |

## 1. 概要

フォローしたい人を見つけるための機能。講義の「ユーザーをどうやって検索するかも詰めておきたい」に対して、次の **4つの入口** を用意する（ユーザーと決めた）。

| 入口 | 場所 | 詳しくは |
|---|---|---|
| ① ユーザー検索 | 検索画面（S-08）で名前の一部を入れる | この文書 |
| ② コメントの一覧 | 投稿の詳細（S-04）の、コメントした人の横のフォローボタン | [comment.md](comment.md) 4.2 |
| ③ いいねした人の一覧 | 投稿のいいね数を押して開く一覧（M-02）のフォローボタン | [like.md](like.md) 4.3 |
| ④ プロフィールへの移動 | 投稿・コメント・一覧のアイコンや名前を押す → プロフィールのフォローボタン | この文書 4.2 |

フォローボタンは、どこでも同じ部品（[profile.md](profile.md) 4.3）。

## 2. 誰が使えるか

ログインしている人。

## 3. 入力と制限（US-01）

| 項目 | ルール |
|---|---|
| 検索の言葉 | 1〜50文字。前後の空白は取り除く。先頭の `@` は無視する（`@taro` でも `taro` でも同じ） |
| 探す対象 | **ユーザー名**と**表示名**の、どちらかに言葉を**含む**ユーザー（部分一致） |
| 文字の違い | 大文字・小文字、全角・半角は同じとみなす（「ＴＡＲＯ」でも「taro」が見つかる。半角の「ﾀﾛｳ」でも「タロウ」が見つかる） |
| 記号 | `%`・`_` も、ただの文字として探す（「%」で全員が見つかったりしない） |
| 自分 | 結果に出してよい（フォローボタンは出さない） |
| 並び順 | ① ユーザー名が言葉と完全に同じ人 → ② ユーザー名・表示名が言葉で始まる人 → ③ それ以外。同じ順位の中はフォロワーの多い順（それも同じなら、先に登録した人） |
| 件数 | 20件ずつ（スクロールで続き） |

## 4. 処理の流れ

### 4.1 ユーザー検索（US-01）

1. 画面の左のメニュー（スマホは下のメニュー）の「検索」で、検索画面（S-08）を開く
2. 検索欄に言葉を入れる。入力が止まって0.3秒たったら検索する（Enter でも検索。日本語の変換中は検索しない）
3. 結果を一覧で出す。1件に出すもの：アイコン・表示名・@ユーザー名・「フォローされています」・自己紹介（1行まで）・フォローボタン
4. 名前やアイコンを押すと、その人のプロフィールへ
5. 検索の言葉は URL に入れる（`/search?q=taro`）。戻る・再読み込みでも同じ結果

### 4.2 プロフィールへの移動（US-02）

- 投稿・コメント・ユーザーの一覧に出る**アイコン・表示名・@ユーザー名**は、すべてその人のプロフィール（`/users/{ユーザー名}`）へのリンクにする

## 5. 表示

## 7. この文書で新しく決めたこと

次の3つは 2026-11-21 にユーザーが確認した（講義のスクショで合わせるものはない）。

- 入力が止まったら自動で検索する（検索ボタンは置かない）
- 並び順：完全一致 → 前方一致 → 部分一致、同じ順位はフォロワーの多い順
- おすすめユーザー（「おすすめユーザー」の欄）は作らない

検索のサーバーのとき（2026-11-21）に決めたこと：

- 続きの読み方は「何人目から」（`offset`。ユーザーの決定）。並びが「一致の順位＋フォロワー数」なので、フォローの一覧のような ID の目印（`before`）は使えないため。読んでいる途中でフォロワー数が変わると並びがずれることがあるが、画面は同じ人を2回出さない
- API の住所は `GET /api/users?q=`。`/api/users/search` にすると、「search」という名前のユーザーのプロフィール（`/api/users/{ユーザー名}`）とぶつかるため
- 全角・半角、大文字・小文字は、言葉と表示名の両方を NFKC（Unicode の「見た目が同じ文字を1つにそろえる」決まり）でそろえてから小文字にして比べる（DB は `lower(normalize(表示名, NFKC))`）。ひらがなとカタカナは別の文字とみなす
- 文字数（50文字）は、そろえる前の言葉（前後の空白と先頭の `@`・`＠` を取ったもの）で数える。画面と同じ数え方にするため（NFKC には「㍿」→「株式会社」のように文字が増えるものがある）
- 部分一致を速くする仕組み（`pg_trgm`）は、今は使わない（[database-design.md](../database-design.md) 4章）

検索の画面のとき（2026-11-21）に決めたこと：

- URL には打った言葉をそのまま入れる（途中・最後の空白も。「山田 」まで打って止まったときに空白が消えないように）。空白だけなら入れない
- 言葉が変わるたびに履歴を増やさない（「戻る」で検索の前の画面へ戻る。プロフィールへ移ってから「戻る」と、同じ言葉の結果に戻る）
- 言葉がないときは、開いたらすぐ検索欄に打てるようにする。言葉があるとき（戻ってきたとき）は、スマホのキーボードが急に出ないよう何もしない
- 51文字以上は、欄の下に「検索する言葉は50文字以内で入力してください」と出し、検索しない
- 打っている間（入力が止まって0.3秒たつまで）は、前の言葉の結果を出したまま。検索を始めたら一覧を消し、読み込み中のくるくるを出す
- 空のフォロー中タブ（[timeline.md](timeline.md) 3章）には「ユーザーを検索」ボタンを出す

## 8. API

> URL・送るもの・返事の形の細かいところは、**API 仕様書（Swagger）を正とする**（開発中に `http://localhost:8081/swagger-ui.html` で開き、その場で試せる。本番では出さない）。この章には、理由・エラーの文言・決めたことを書く。

ログインが必要。

| メソッド・URL | 送るもの | 返事 |
|---|---|---|
| GET `/api/users?q=…&offset=…` | `q`：検索の言葉。`offset`：何人目から読むか（なければ 0） | 200 `{ users: [FollowUser], nextOffset }`。20件ずつ。続きは `offset` に `nextOffset` を入れて読む（なければ `null`）／400 `VALIDATION_ERROR`（`errors[].field` は `q`：「検索する言葉を入力してください」「検索する言葉は50文字以内で入力してください」。`offset` が負のときは `offset`） |

- 1人の形 FollowUser は、フォロー中・フォロワーの一覧と同じ（[profile.md](profile.md) 8章。`id`・`username`・`displayName`・`bio`・`iconUrl`・`following`・`followedBy`）。メールアドレスは入れない
- 自分も結果に出る（画面は自分にフォローボタンを出さない）
- フォロワー数とフォローの状態は、同じ SQL の中で読む。20人でも SQL は増えない
