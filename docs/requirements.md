## 1. 概要

### 1.1 目的

X（旧 Twitter）のような、タイムライン形式のテキスト中心の SNS アプリを作る。RaiseTech 中級編の課題として、要件定義から設計・開発・AWS へのデプロイまでを学ぶ。

### 1.2 背景（課題の条件）

- 講義の指示に沿って、**要件定義のドキュメント（要件定義書・機能定義書・画面設計書・ER 図・インフラ構成）から作る**
- 講義で示された機能：ログイン・タイムライン・コメント・いいね・画像投稿
- それに加えて、新規登録・プロフィール・フォロー・ユーザー検索を作る（ユーザーの判断）
- X との違い：インプレッション数（表示回数）とリツイートは作らない（講義の方針）

### 1.3 利用者

| 項目 | 内容 |
|---|---|
| 利用者 | 受講生や個人。**複数のユーザーが使う前提**で設計する |
| 他の人との関わり | 他の人の投稿を見る・いいねする・コメントする・フォローする |
| ログイン | 新規登録・ログイン画面以外は、ログインしないと見られない |

### 1.4 用語

| 用語 | 意味 |
|---|---|
| ユーザー | 新規登録をした利用者 |
| ユーザー名 | `@taro_dev` のような、ユーザーごとに重ならない ID。URL にも使う |
| 表示名 | 画面に大きく出す名前（例：山田 太郎）。他の人と同じでもよい |
| 投稿 | 280文字までの文章（＋画像4枚まで、または動画1本）。X の「ポスト」にあたる |
| 返信 | コメントに付けたコメント |
| タイムライン | 投稿を新しい順に並べた一覧。「すべて」と「フォロー中」の2つ |
| フォロー | 他のユーザーの投稿を「フォロー中」タイムラインに出すための登録 |
| フォローバック | 自分をフォローしている人を、自分からもフォローすること |

## 2. 機能要件

機能の一覧は **[機能一覧（features.md）](features.md)**、機能ごとの細かい決まりは `features/` の機能定義書にまとめる。ここでは全体の要点だけを書く。

| 区分 | 要点 | 機能定義書 |
|---|---|---|
| 認証 | メールアドレスとパスワードで新規登録・ログイン・ログアウト | [authentication.md](features/authentication.md) |
| タイムライン | 「すべて」（全員の投稿）と「フォロー中」（自分＋フォローした人）の2つのタブ。新しい順 | [timeline.md](features/timeline.md) |
| 投稿 | 本文は1〜280文字。画像は4枚まで、または動画1本（MP4・100MB・2分20秒まで）。どちらも S3 に保存。自分の投稿は編集・削除できる | [post.md](features/post.md) |
| コメント | 他の人の投稿にもコメントできる。コメントへの返信もできる（X と同じ）。1〜280文字。自分のコメントは削除できる | [comment.md](features/comment.md) |
| いいね | 投稿とコメント（返信を含む）に、1人1回。取り消せる。いいね数と、いいねした人の一覧を見られる | [like.md](features/like.md) |
| プロフィール・フォロー | 表示名・自己紹介・アイコン画像。フォロー・フォロー解除・フォローバック。フォロー数・フォロワー数と一覧 | [profile.md](features/profile.md) |
| ユーザー検索 | ユーザー名・表示名の部分一致で探す。コメント一覧・いいねした人の一覧からもフォローできる | [user-search.md](features/user-search.md) |

## 3. 非機能要件

ID の頭文字：N = 非機能（Non-functional）。

### 3.1 使いやすさ・表示

| ID | 内容 |
|---|---|
| N-01 | パソコンとスマホの両方で使える。スマホは横幅 320px 以上で、表示が崩れたり横にはみ出したりしないこと |
| N-02 | 対応ブラウザ：パソコンの Chrome・Edge・Firefox・Safari、iPhone の Safari、Android の Chrome（それぞれ最新版） |
| N-03 | 入力の誤りは、どの項目がなぜだめかを日本語で表示する |
| N-04 | 投稿・コメントの削除の前には確認を出す |
| N-05 | 投稿・コメントの入力中は、残りの文字数を表示する |
| N-06 | 日時は「3分前」「2時間前」「11月8日」のように、今からの近さに合わせて表示する |

### 3.2 性能

| ID | 内容 |
|---|---|
| N-11 | 同時に使う人は10人ほどと想定する |
| N-12 | 投稿が1万件あっても、タイムラインの最初の20件がおおむね1秒以内に出る |
| N-13 | タイムラインは20件ずつ読み込む（下までスクロールしたら続きを読む） |

### 3.3 セキュリティ

| ID | 攻撃・リスク | 対策 |
|---|---|---|
| N-21 | 通信の盗み見 | 本番の通信は HTTPS にする（CloudFront で付ける） |
| N-22 | パスワードの漏えい | BCrypt でハッシュ化して保存する |
| N-23 | パスワードの総当たり | 同じ接続元からのログインの失敗は、15分に10回までにする |
| N-24 | 他人のデータの操作 | 投稿・コメントの編集や削除は、サーバー側で毎回「本人のものか」を確かめる |
| N-25 | SQL インジェクション | MyBatis の SQL では、値を必ず `#{}`（値として安全に渡す書き方）で渡し、`${}`（文字列をそのまま埋め込む書き方）は使わない。SQL を文字列の連結で作らない |
| N-26 | XSS | React の自動エスケープに任せ、`dangerouslySetInnerHTML` は使わない |
| N-27 | ログイン状態の盗用 | JWT（ログインの証明書）は HttpOnly の Cookie に入れ、画面の JavaScript から読めないようにする。期限を付ける |
| N-28 | 画像・動画に見せかけたファイル | アップロードされたファイルは、中身が本当に画像・動画（MP4）かをサーバーで確かめる。だめなら S3 からも消す |
| N-29 | 秘密情報の漏えい | パスワードや AWS の鍵はコードや Git に書かない。本番は AWS の Parameter Store に入れる |
| N-30 | DB への直接攻撃 | DB（RDS）はインターネットに公開せず、EC2 からだけ接続できるようにする |
| N-31 | 内部情報の漏えい | エラーの詳細（スタックトレース）を画面や API の返事に出さない |

### 3.4 運用・保守

| ID | 内容 |
|---|---|
| N-41 | DB は RDS の自動バックアップを使う（7日分） |
| N-42 | エラーはログに残し、原因を後から調べられるようにする。パスワードやトークンはログに残さない |
| N-43 | サーバー側・画面側それぞれ自動テストを用意し、GitHub の PR で自動で実行する |
| N-44 | AWS の費用は、クレジットの範囲に収める。使わないときは止める・片付ける |

## 5. 対象外（今回は作らないもの）

| 機能 | 作らない理由 |
|---|---|
| リツイート（リポスト）・引用 | 講義の方針（X との違い） |
| インプレッション数（表示回数） | 講義の方針（X との違い） |
| DM（ダイレクトメッセージ） | 投稿とは別の仕組みが必要で、大がかりになる |
| 通知（いいね・フォローされたなど） | 今回の機能に入っていない |
| ブロック・ミュート・鍵アカウント | 今回の機能に入っていない |
| ハッシュタグ・投稿の検索 | 検索はユーザー検索だけにする |
| 動画の変換（iPhone の MOV・HEVC を再生できる形にするなど） | 変換の仕組み（MediaConvert など）が必要で、作りと費用が増える。動画は MP4（H.264）だけ受け付ける |
| パスワードの再設定・メールアドレスの確認 | メールを送る仕組みが必要 |
| 退会 | 後回し（作るなら、投稿・コメント・いいね・フォローも一緒に消す） |
| おすすめ（アルゴリズムで選ぶタイムライン） | タイムラインは新しい順だけ |
