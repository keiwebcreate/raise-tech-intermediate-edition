## 基本設定
- 応答はすべて日本語で行う

## このプロジェクト

RaiseTech 中級編の課題で作る、X（旧 Twitter）のようなタイムライン形式の SNS アプリ「RaiseTechtimeline」。

- **講義のスクショを見ながら進める。** 技術や手順は講義の指示を優先する。講義と違うやり方をしたくなったら、先に相談する
- 複数のユーザーが使う前提（他の人の投稿にいいね・コメント、フォローができる）
- 新規登録・ログイン画面以外は、ログインしないと見られない
- 講義で使っている「タスクマネジメント」プロジェクトは手元にない。代わりに前の課題（`../beginner_version`＝トレロ風アプリ、`../beginner_edition_final_assignment`＝レシピ管理アプリ）の文書と作り方を参考にする

## 決まっていること（必ず守る）

- 投稿とコメントの本文は **280文字まで**
- 投稿には **画像4枚まで、または動画1本**（混ぜない）。動画は MP4・100MB・2分20秒まで
- 画像・動画は **S3 に保存**する（DB には S3 のキーだけ持つ）。動画はブラウザから S3 へ直接送る
- コメントには **返信**でき（何段でも）、コメントにも**いいね**できる（X と同じ）
- タイムラインは「すべて」と「フォロー中」の **2つのタブ**
- リツイートとインプレッション数は作らない
- AWS は **シドニーリージョン（ap-southeast-2）** を使う。**東京は使わない**（組織の設定で断られる）
- HTTPS は **CloudFront** で付ける（CloudFront → ALB → EC2 → RDS。独自ドメインは使わない）
- Node.js は **24**（AWS でのデプロイで 24 が必要）

- バージョンは記憶に頼らず、その時点の最新を調べてから書く（講義の指定があればそちらを優先）

## GitHub の運用ルール（必ず守る）

リポジトリ：（まだ作っていない。作ったらここに書く）。GitHub の操作（イシュー・PR・設定）は `gh` コマンドで行う。作業は次の流れで進める。

1. **イシューを立てる**：作業を始める前に、必ずイシューを作る。作る前に中身を私に見せて確認をとる（私がその作業を頼んだときは、そのまま作ってよい）
2. **ブランチを切る**：最新の `main` から、イシュー1つにつきブランチを1つ作る
3. **コミット・プッシュ**：作ったブランチにコミットしてプッシュする
4. **PR を作る**：`gh pr create` で `main` 向けの PR を作る（承認なしで作ってよい）
5. **マージは私が GitHub の画面で行う**：Claude はマージしない。**マージしてほしいときは「PR #○ をマージしてください」とはっきり頼む。** マージ後は `main` に戻って `git pull` する

- **`main` へ直接コミット・プッシュしない**（リポジトリを作ったら、GitHub のルールセットでも禁止する）

### イシュー
- 本文は次の4つの見出しで書く：「目的」「やること」（チェックリスト）「完了条件」（チェックリスト）「関係する設計書」
- 種類に合ったラベルを付ける（`enhancement`・`bug`・`documentation` など）

### ブランチ名
- 形は `種類/イシュー番号-内容`。内容は英小文字とハイフン（例：`feature/12-timeline`、`fix/15-login-error`）
- 種類は `feature`（機能）・`fix`（不具合）・`docs`（文書）・`chore`（設定・雑務）・`test`（テスト）・`refactor`（作り直し）

### コミットメッセージ
- 形は `種類: 内容`。内容は日本語で書く（例：`feat: 投稿の API を追加`）
- 種類は `feat`・`fix`・`docs`・`chore`・`test`・`refactor`（ブランチの `feature` はコミットでは `feat`）
- 本文の最後に `Refs #番号`（途中のコミット）を書いてイシューと結びつける

### PR
- タイトルはコミットメッセージと同じ形にする（Squash and merge で、そのまま `main` のコミットになる）
- 本文には「やったこと」「確認したこと」（実行したテストと結果）を書き、最後に `Closes #番号` を書いてイシューと結びつける

### GitHub の設定（リポジトリを作ったら行う）
- `main` のルールセット：PR 必須（承認は0人）、強制プッシュと削除の禁止。管理者も例外なし
- マージ方法は Squash and merge だけ。マージしたブランチは自動で削除する
- GitHub Actions を作ったら、テストの成功を必須にするルールを足す
- `.github/workflows/` を変えた push が Git Credential Manager のログインで断られたら（`workflow` の権限がない）、`git -c credential.helper= -c "credential.https://github.com.helper=!gh auth git-credential" push` で送る

### ポートとデータベース（必ず守る）
- ポートは **5174（Vite）・8081（Spring Boot）・5433（PostgreSQL）**。**別のポートでは起動しない**。使われていたら、使っているものを止めてから決まった番号で起動する
  - 前のアプリと同時に動かしてもぶつからないように、番号をずらしてある（トレロ風アプリは 5173・8080・5432、レシピアプリは 3000・8000・3308）
- 開発中はブラウザで `http://localhost:5174` を開く。`/api` は Vite が Spring Boot（8081）へ転送する
- **3306 は別のプロジェクトの Docker MySQL なので触らない**
- DB は `sns_app`（開発）、ユーザーは `sns_app_user`。パスワードは Windows のユーザー環境変数 `SNS_DB_PASSWORD`（中身を表示しない。環境構築のときに私が登録する）
- パスワード・JWT の鍵・AWS の鍵などの秘密の情報は、コードにも Git にも書かない。環境変数で渡す（本番は AWS の Parameter Store）
- 開発中の画像の保存先も S3 にするか、パソコンのフォルダにするかは、詳細設計で決める
- 動作確認でサーバーを起動・停止するときは、スキル **`dev-servers`** の手順で行う。チャットを終えるときは、起動したサーバーを止める

## サーバー（Spring Boot）のルール（トレロ風アプリと同じ。詳細設計で確定する）

- パッケージは `io.github.keiwebcreate.raisetechtimeline`（予定）。機能ごと（`auth`・`user`・`post`・`comment`・`like`・`follow`）と `common` に分ける
- API だけを作る（画面は React）。URL は `/api/...`
- ログインは JWT（講義の方針）。JWT は HttpOnly の Cookie に入れる（要件 N-27）
- Controller → Service → Repository の3層。Controller に判断を書かない。変更する Service のメソッドには `@Transactional`
- API の JSON は DTO（`record`）で受け取り・返す。エンティティをそのまま返さない
- **本人の確認**：投稿・コメントの編集や削除は、必ず「ID ＋ 本人」の条件で探す。他人のものは 404 にする
- ルール違反は独自の例外を投げ、まとめて Problem Details（エラーの決まった形の JSON）に変換する。Controller に try-catch を書かない
- テーブルの変更は Flyway の SQL ファイルを追加して行う。すでにあるファイルは書き換えない
- 画像は、中身が本当に画像かを確かめてから S3 に保存する
- エラーの詳細・パスワード・トークン・メールアドレスをログやレスポンスに出さない

## 画面（React）のルール（詳細設計で確定する）

- TypeScript で書く。`any` は使わない
- フォルダは `features/`（機能ごと）と `shared/`（共通）に分ける
- API は1つの共通の関数（例：`src/api/client.ts`）を通して呼ぶ
- `dangerouslySetInnerHTML` は使わない
- Enter で送信する入力欄では、日本語の変換中（`isComposing`）は送信しない
- 文字数は画面・サーバー・DB で同じ数え方にする（絵文字も1文字）
- 画面の文言・メッセージは `screen-design.md` のとおりにする
- 横幅 320px でも崩れないことを確かめる
