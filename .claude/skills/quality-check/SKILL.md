# 品質チェック

コードを**変えずに読むだけ**で確かめ、決まった形で報告する。直すのは、報告を見たユーザーと相談して決めてから。コマンドは `Intermediate_edition` フォルダを基準にする。

> 環境構築の前に書いた手順。チェックの道具（Checkstyle・oxlint など）を入れたら、1 の表を実際のコマンドに合わせて直す。

## 0. 範囲を決める

ユーザーの頼み方で決める。はっきりしなければ、PR の前なら「差分だけ」、それ以外は「全体」。

| 範囲 | 読むもの |
|---|---|
| 全体 | `backend/src`・`frontend/src` のすべて |
| 差分だけ | `git diff main...HEAD` と `git status` に出るファイル。変わった部分を使う側・呼ばれる側も必要に応じて読む |
| インフラ | AWS の構成のファイル・EC2 に置く設定（作ったら、ここに場所を書く） |
| 文書 | `docs/` の設計書どうしの食い違い（機能一覧・機能定義書・画面・テーブルの対応） |

## 1. 自動チェック

すべて実行して、成功・失敗と、指摘の件数・場所を集める。

| 場所 | コマンド（予定） | 中身 |
|---|---|---|
| サーバー | `.\gradlew.bat check`（`backend`） | テストとコードのチェック |
| 画面 | `npm run lint`（`frontend`） | コードのチェック |
| 画面 | `npm test` | Vitest |
| 画面 | `npm run build` | 型チェックと本番用の作成 |

- 範囲が「差分だけ」（PR の前）のときは、Claude Code の公式のスキル **`security-review`** も走らせる
- 「警告」も数えて報告する
- 規則を外したい指摘があっても、勝手に設定を変えない（報告して相談する）

## 2. AI の見直し

設計書（`docs/`）と `.claude/CLAUDE.md` のルールを基準に、コードを読む。次の観点は毎回必ず見る。

**サーバー（Spring Boot）**
- 本人の確認：投稿・コメントの編集や削除で「ID ＋ 本人」の条件で探しているか。他人のものは 404 か
- 他人のデータとの関係：いいね・コメント・フォローは他人の投稿・ユーザーに対して行えるか。自分自身をフォローできないか
- 重なり：同じ投稿に2回いいね・同じ人を2回フォローしたとき（同時に押されたときも）、一意制約の違反で 500 にならないか
- 文字数：投稿・コメントの280文字が、絵文字を含めて画面・サーバー・DB で同じ数え方か
- 画像：中身が本当に画像か、大きさの上限、S3 のキーの作り方（利用者が決めた名前をそのまま使っていないか）
- 例外：想定外の入力（URL の ID に数字以外、JSON の形の違い）が 400・404 などになり、500 にならないか
- `@Transactional`：変更する Service のメソッドに付いているか。読むだけなら `readOnly = true`
- 一覧の読み込み：タイムラインやいいね数で、1件ごとに SQL が走っていないか（N+1 問題）
- ログとレスポンス：パスワード・JWT・メールアドレス・エラーの詳細が出ていないか

**画面（React）**
- フック：依存の漏れ・余分
- アクセシビリティ：モーダル（Tab でフォーカスが後ろに抜けないか）、押せる要素はボタンか、入力欄に名前（label・aria-label）があるか
- API：共通の関数を通しているか。API が成功してから画面を変えているか（いいね・フォローの表示を先に変えるなら、失敗したら元に戻すか）
- 文言：メッセージが `screen-design.md` のとおりか

**画面とサーバーの食い違い**
- 入力チェックのルール（必須・文字数・形式）が両方で同じか
- 前後の空白：画面で取り除いて確かめた値と、送っている値が同じか

**日本語ならではの点**
- Enter で送る入力欄で、変換中（`isComposing`）は送らないか
- ユーザー検索で、全角・半角、大文字・小文字の扱いが機能定義書のとおりか

**インフラ**（設計の正は `docs/infrastructure.md`）
- 入口：セキュリティグループが必要なポート・必要な相手だけか。Spring Boot と RDS が外から届かないか
- S3：バケットを公開していないか。EC2 のロールの権限が、そのバケットだけか
- 秘密の値：パスワード・鍵が Git・ログ・コマンドの引数に出ていないか
- 料金：高いもの（NAT ゲートウェイなど）を足していないか。足すなら料金を報告する
- リージョンがシドニー（ap-southeast-2）か

## 3. 裏付け

疑わしい点は、報告の前に確かめる。推測のまま「不具合」と書かない。確かめられなかったものは「未確認」と書く。

## 4. 報告

次の形で出す。専門用語には短い説明を添える。

1. **結論**（1〜2文。大きな問題があるか）。よくできている点も短く書く
2. **自動チェックの結果**：コマンドごとに成功・失敗、指摘の件数
3. **指摘の表**：次に分け、それぞれ「#・場所・内容・直し方」の表にする。番号は通し番号
   - 不具合（実際に困ることがあるもの）
   - セキュリティ（どの要件 N-xx に当たるかを書く）
   - 標準から外れているもの
   - チェックの道具
   - 細かいもの
4. **質問**：どこまで直すかを、おすすめと選択肢を示して1つ聞く

## 5. 直すとき

- 直すのは、ユーザーが範囲を決めてから。いつもの「イシュー → ブランチ → PR」の流れで進める（`.claude/CLAUDE.md`）
- 直したら 1 の自動チェックをもう一度すべて通し、PR の「確認したこと」に結果を書く

## つまずいた点のメモ

（前のアプリで分かったこと。このアプリでも起きそうなもの）

- **Prettier などでほぼ全部のファイルが「違う」と出る**：この PC の Git は `core.autocrlf=true` で、改行を CRLF に変える。書き方の道具の設定で改行を `auto` にする
- **Git Bash で `cd` のたびに `fnm` のエラーが出る**：`cd … && 次のコマンド` が止まることがある。`git -C`・`-chdir` などで `cd` を避けるか、PowerShell を使う
- **サーバーのテストが全部失敗する（`Could not connect to Ryuk`）**：Docker Desktop の通信の不調。パソコンを再起動する
